# Model Card & Responsible AI Reflection — TuneMatch

This document is the graded responsible-AI reflection for the TuneMatch applied AI system (see [`README.md`](README.md) for the project overview, architecture, setup instructions, and general testing summary). It answers four questions directly and honestly, grounded in what was actually observed while building and testing this specific system — not generic AI-safety boilerplate.

## Dataset Description

The song catalog (`music_recommender/demo_catalog.py`) is 18 hand-curated songs spanning 18 genres — indie pop, dream pop, pop, lofi, rock, metal, folk, edm, jazz, classical, ambient, hip hop, reggae, country, synthwave, punk, r&b, and blues — chosen deliberately broad rather than deep (mostly one song per genre) so the retrieval and ranking logic gets exercised across a wide range of tag combinations rather than being tuned to one musical style.

Each song (`Song` in `music_recommender/data.py`) carries 8 attributes: `title`, `artist`, `genre`, `mood`, `themes` (a short list of lyrical/thematic tags), `lyrics_excerpt` (a one-line excerpt used for semantic retrieval and grounding explanations), and three audio features on a 0.0–1.0 scale — `energy`, `valence`, and `acousticness` — compared against the specialized model's predicted target profile.

**Intended purpose:** this dataset exists to demonstrate the retrieval, ranking, diversity, and specialized-model components working across genuinely different musical contexts — it is explicitly a small, hand-labeled demonstration dataset, not a production catalog. See Limitations below for what that scope trade-off costs.

## Algorithmic Approach (Plain Language)

In plain terms, here's what happens between a listener describing their taste and getting a recommendation:

1. **Compare against every song three ways.** For each song in the catalog, the system checks: does its genre/mood/theme/artist exactly match what the listener said? Does its lyrics/theme *meaning* resemble what they described, even without an exact tag match (via AI embeddings)? Does its actual sound (energy, positivity, acousticness) resemble the sound a small trained model predicts the listener would enjoy, based on their stated genre and mood?
2. **Combine those three signals into one score.** A chosen "ranking strategy" decides how much weight each signal gets — by default they're blended fairly evenly, but the system can instead prioritize genre matches, mood matches, or overall sound above the others.
3. **Build the final list one pick at a time, favoring variety.** Rather than just taking the top-scoring songs, the system picks the best remaining song, then slightly penalizes any later song that shares an artist or genre with something already picked — so the final list doesn't collapse into five songs by the same artist.
4. **Explain the pick in plain language.** For each recommendation, an AI model is asked to write a short, personalized explanation grounded only in the evidence gathered in step 1 — or, if that's unavailable, a template fills in the same evidence as a plain sentence instead.

## What are the limitations or biases in your system?

- **The specialized model's training set is tiny and synthetic.** `TasteAffinityModel` is trained on 29 hand-written (genre, mood) → (energy, valence, acousticness) rows, not real listening or audio-analysis data. This was proven, not assumed: a stress test with `classical` + `euphoric` (a combination absent from training) predicted `{energy: 0.42, valence: 0.52, acousticness: 0.54}` — essentially the training set's average — rather than leaning toward either stated preference. The model doesn't fail loudly on unfamiliar input; it quietly regresses to a bland, generic answer. That's a subtler and more dangerous failure mode than a crash, because a plausible-looking number in `[0, 1]` doesn't announce that it's meaningless.
- **This reproduces the exact bias the original TuneMatch documented, just in a new component.** The Module 3 model card's central finding was that its heaviest-weighted signal (energy) created a "safe middle" filter-bubble effect — mid-energy songs got recommended to everyone because they were never far from anyone's target. The new specialized model has the same failure shape: for any taste combination sparse in its training data, it hedges toward the dataset's average rather than genuinely representing that listener. Rebuilding the system with a trained model didn't remove this bias; it relocated it.
- **Categorical matching is still exact-string.** `"indie"` and `"indie pop"` are unrelated to the matcher (`retriever.py`), exactly as documented in the source project. Semantic (Voyage) retrieval is supposed to compensate for this, but every demo and test run in this project's history ran with `VOYAGE_API_KEY` unset — meaning the semantic-matching safety net was never actually exercised end-to-end. It's implemented and unit-tested against a fake embedding client, but its real-world behavior on messy genre labels is unverified.
- **The demo catalog is still small (18 songs)**, and while it now spans 18 genres deliberately (see Dataset Description above), most genres have exactly one song. A listener whose taste doesn't map onto the catalog's vocabulary at all (the `kpop` test case is a direct example) gets a response, but not a good one — the system falls back to whatever weak signal exists rather than admitting it has nothing relevant. Real deployment would need a catalog several orders of magnitude larger before this stopped being the dominant limitation.
- **The LLM explanation path (`explainer.py`) was never run live.** Every "AI-generated" explanation shown in this project's documentation is actually the deterministic template fallback, because `ANTHROPIC_API_KEY` was never set during development. The prompt is designed to ground Claude strictly in retrieved evidence and instructed not to invent facts, and `check_explanation_groundedness` provides a shallow automated check (non-empty, names the listener, isn't absurdly long) — but that heuristic would not catch subtle hallucination (e.g., a fabricated lyric or a misattributed influence). The live generation path is implemented and reviewed, not empirically validated.
- **Scoring weights are hand-chosen, not learned or user-validated** (`SEMANTIC_WEIGHT = 3.0`, `AUDIO_WEIGHT = 1.5`, `SEMANTIC_MATCH_THRESHOLD = 0.5` in `recommender.py`/`retriever.py`). They were picked because they produced sensible-looking rankings on a handful of test profiles, the same way the original TuneMatch's energy weight was picked — which is exactly the kind of unaccountable design choice its own model card warned about.

**Improvement ideas, in priority order:**

1. **Replace the synthetic 29-row training set with real audio-feature data** (e.g., a public dataset of Spotify audio features, or the Spotify Web API's own `/audio-features` endpoint for the catalog's actual songs). This directly targets the biggest proven weakness — the specialized model regressing to the mean on untrained genre/mood combinations — since a model trained on thousands of real (genre, mood, energy, valence, acousticness) rows would have far more to interpolate from than 29 hand-written ones.
2. **Add a real collaborative signal alongside the content-based one.** Right now the system only knows a song's own attributes, never how other listeners with similar taste responded to it. Even a small "listeners who picked X also liked Y" table computed offline from synthetic interaction data would let the system recommend on more than tags and audio features alone — closer to how the real-world systems described earlier in this document actually work.

## Could your AI be misused, and how would you prevent that?

- **Mood-based profiling beyond music recommendation.** The taste-affinity model's mood input, and the taste-profile data structure generally, could be repurposed as a lightweight signal for inferring emotional or mental-health state rather than music preference — a "reflective, melancholic, nostalgic" profile is not a neutral input outside this context. This project mitigates that only by scope: nothing persists a taste profile to disk or a database (it's an in-memory dataclass for the duration of one request), and the trained model is never exposed as a general-purpose mood classifier. A production version would need to make that scope boundary an explicit, enforced constraint, not just current behavior.
- **LLM-generated content misattributed to real artists.** Once live, `ClaudeExplainer` writes text that references real song titles, real artists, and real (short) lyric excerpts. If the grounding in retrieved evidence ever failed silently, the system could generate a plausible-sounding but false claim about a real, named artist (e.g., asserting a thematic connection that doesn't exist). The prompt explicitly instructs Claude not to invent facts and to stick to the retrieved evidence, and `stop_reason == "refusal"` is checked before trusting output — but as noted above, this was never verified against a live API, so "the mitigation exists in the prompt" is not the same claim as "the mitigation was observed working."
- **Credential exposure.** Both `VOYAGE_API_KEY` and `ANTHROPIC_API_KEY` are read exclusively from environment variables — never hardcoded, never written to a committed file, never logged. If either leaked, the blast radius is API cost/abuse on those services, not access to any user data (since none is persisted).
- **Catalog/lyrics provenance.** Nothing in this system verifies that a song's `lyrics_excerpt` is used within fair-use bounds or that catalog metadata is accurate. At demo scale (hand-entered, short excerpts) this is low-risk; scaling the catalog with scraped or unlicensed lyrics data would need real content-provenance and licensing checks that this project doesn't implement.

## What surprised you while testing your AI's reliability?

The most useful surprise was the shape of the `classical` + `euphoric` failure described above: I expected a stress test on an unusual genre/mood combination to either produce an obviously wrong result or to fail outright. Instead it produced a *quietly* wrong result — a valid-looking number that carried no real signal. That's a more important finding than a crash would have been, because a crash is caught by any basic test; a confident-looking wrong answer is the failure mode that actually reaches a user.

The second surprise was more about the testing process itself: naively checking "does the same input always produce the exact same output" doesn't work once part of the pipeline is an LLM — Claude is *expected* to phrase the same grounded facts differently across calls, so a strict text-equality check would flag correct behavior as a bug. `check_consistency` had to be scoped deliberately to only the parts of the pipeline that are supposed to be deterministic (which songs get retrieved, their score, their rank), while explanation quality is checked separately and more loosely. That distinction — knowing which parts of an AI system are supposed to vary and which aren't, and testing each accordingly — wasn't obvious going in.

The third: how much of this project's demonstrated "AI behavior" turned out to be running through fallback paths rather than the live AI services, simply because no one ever set the two API keys during development. The system is honest about this in its logs (every run prints a `WARNING` naming exactly which key is missing), but it means the retrieval and explanation quality documented in the README's Sample Interactions have not actually been validated against the real Voyage and Claude services — only against their designed-for-failure fallback paths, plus the one component (the scikit-learn taste-affinity model) that needed no external key and so was the only AI component verified running live.

## Diversity / Fairness Component (Stretch Feature)

`MusicRecommender._diversify` (`recommender.py`) is this project's fairness mechanism: while building the final top-`limit` list, it subtracts a penalty each time a candidate song's artist (`ARTIST_PENALTY = 2.0`) or genre (`GENRE_PENALTY = 0.75`) already appears among the picks made so far, and greedily re-ranks around those penalties rather than just sorting by raw score. It's a direct callback to the original TuneMatch's own diversity re-ranking — see the limitations section above: this project's specialized model reintroduced a "safe middle" filter-bubble bias in a new form, and this component is the mitigation for the *equivalent* bias in retrieval — recommendations collapsing onto whichever single artist or genre happens to score highest, rather than reflecting the breadth of what actually matched.

**How it improves fairness:** without this, a listener with broad taste that happens to line up well with one prolific artist or one dominant genre would see their entire recommendation list monopolized by that single artist/genre — every other reasonable match gets crowded out even though it was genuinely relevant. That's a real fairness concern for *songs and artists*, not just listeners: an artist with 3 catalog entries that all happen to score well would take 3 of 3 recommendation slots, permanently squeezing out every other artist for that listener, regardless of how good those other matches were. The penalty makes room for a second-best match from a different artist/genre once the top slot is taken, and — importantly — it's transparent about doing so: the affected recommendation's explanation says outright "(Ranked slightly lower to keep your list varied...)" rather than silently reordering with no explanation, which the original TuneMatch's diversity mechanism also did.

**Verified, not just implemented:** a constructed test (`tests/test_recommender.py::test_diversity_penalty_prevents_a_single_artist_sweep`) proves it changes real output — given three strong matches from "Artist A" and one weaker match from "Artist B", the undiversified ranking would be A1, A2, A3 (Artist A sweeps all three slots); the actual system output is A1, B1, A2 — Artist B is pulled into 2nd place instead of being shut out entirely. One honest limitation: the project's own 18-song demo catalog happens to have no repeated artist or genre, so this component never actually triggers on any of the Sample Interactions in the README — its effect is real and tested, but not visible in this project's own demo data.

## Collaboration with AI

I built this project working with Claude (Claude Code) iteratively, feature by feature, rather than handing over the whole spec at once. Before each major addition — choosing an embeddings provider, deciding what the specialized model should predict, deciding what "reliability testing" should actually check — Claude asked a clarifying question with a recommended option and a stated trade-off instead of just picking an approach unilaterally, and I picked from those options. The system grew in the order: rule-based baseline (Module 3) → hybrid retrieval → LLM-generated explanations → a trained specialized model → an automated reliability/consistency test suite → this documentation, with tests and a real command run (`pytest`, `python app.py`, or the specific script in question) verifying each step before moving to the next, rather than trusting generated code on its own claims.

**A helpful suggestion:** Claude proposed — unprompted, not something I asked for by name — that every external AI dependency (Voyage embeddings, the trained taste-affinity model, Claude's own explanation generation) should fail in the exact same shape: log a warning naming what failed and why, then fall back to a deterministic alternative, rather than crash. This turned out to be the single most load-bearing design decision in the project. Because of it, the entire system stayed fully testable, demoable, and honest about its own state throughout development, even though the two live API keys were never actually configured in this environment — the fallback paths aren't a hypothetical safety net, they're what every test, demo, and README example in this project actually exercised.

**A flawed suggestion:** While adding tests for the LLM-explanation feature, Claude's first attempt at `tests/test_recommender.py` included a nonsensical, dead line of generated code — `fake_explainer = MusicRecommender.__init__.__globals__["ClaudeExplainer"]  # unused, keeps import symmetry` — a leftover fragment from an earlier approach that never got cleaned up, left in with a comment rationalizing its presence rather than removing it. It didn't break anything (the line was never used), but it was exactly the kind of confusing, unjustified code an AI can produce when generating a file in one pass without re-reading its own output. It was caught on the next read-through and replaced with a clean top-level import instead of the dead reference. The lesson: AI-generated code needs the same "does this line actually need to exist" scrutiny as any other code, especially in files that came out of a single large edit rather than incremental, reviewed changes.
